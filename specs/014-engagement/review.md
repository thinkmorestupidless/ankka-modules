# Review: 014 engagement — the brand's CRM, suppression, transactional sends, push and presence

**Verdict:** Request changes
**What it does:** Adds `services/engagement`, which turns the brand's facts into Customer.io identifies, tracks and transactional sends. Each send is a durable `Send` workflow with attempts, a dead letter and outbound suppression. The service also serves the send route, the Customer.io webhook, the player and agent SSE streams, presence, configuration and the seed. It amends `players` (consent facts at registration, a terminal `refused`), `responsible-gambling` (`rg_limit_loosening_requested`), the contract and the module manifest, and adds the crm-stub, the recording driver and 73 recordings.
**Should it exist:** yes. It replaces four overlapping paths in the original with one fact-driven service that has a durable send record. The design (one workflow per send key as the claim, a per-player event-sourced channel, pure ports of the original's rules) matches plan.md and the constitution.
**Read:** In full: every file under `services/engagement/src/main`; the diffs to `services/players`, `services/responsible-gambling`, `contract/`, `modules/engagement/module.json`, `contract/keys.md`, `.github/workflows/ci.yml` and `Justfile`; spec.md, plan.md and tasks.md. Read in part: research.md (*Found during implementation*), data-model.md and contracts/routes.md. Outside the diff: `services/players/.../player/PlayerEntity.scala` (`liftExclusion`), `services/players/.../facts/Facts.scala` (the mapping that is not in the hunk), and ankka's `build/consumers.md` (delivery from a key value entity versus a workflow). Tests read: `it/Facts.scala`, `it/ErasureSuite.scala` and `features/SuppressionFeatures.scala` (the exclusion scenario). The other suites were only skimmed. Not reviewed line by line: the 74 recordings under `tests/port/engagement/` (data), the Go recording driver, crm-captures and crm-seed (`tests/original/`, test tooling run by hand), and crm-stub's internals. Someone who knows the Go tooling should look at those if they are to be kept.
**Size:** 264 files, +163,225 −248. Without the 74 recordings: 190 files, +16,686 −248, of which about 3,750 lines are production Scala and the rest tests, Go tooling and docs. This is well past the size where reviewing still finds defects reliably. The split we would accept next time: (1) the neighbour and contract amendments, (2) the service, (3) the recording tooling and recordings with the parity suite. The recordings are tool output and are not counted against the change.

## Blocking

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/profile/Suppression.scala:28` — issue (blocking): once a player self-excludes, they stay suppressed for good. `player_self_excluded` sets `status = "self_excluded"`, and the check `p.status == "self_excluded" || open(SelfExclusionCase)` keeps the player suppressed for as long as that status holds. Nothing ever changes it back. `players` persists `ExclusionLifted` when an exclusion ends (`PlayerEntity.liftExclusion`), but `Facts.playerFact` maps that event to `None`, so no fact reaches this service. `rg_case_closed` only removes the case. So after an exclusion ends, every identify keeps saying `marketing_suppressed=true` / `self_excluded` and marketing never resumes. That contradicts US3's scenario "an exclusion ending identifies the player as not suppressed and marketing resumes". The bound scenario (`SuppressionFeatures.scala:140`) passes only because its Given opens an RG case and never publishes `player_self_excluded`, so the test cannot fail for the real flow. Suggestion: one option is for `players` to publish a fact for `ExclusionLifted` (an additive contract family), which `Profiles.players` maps to status `active`. The other is to drop the status test and rely on the open case, but only if every exclusion, including an operator's `setSelfExcluded`, opens an RG case; please confirm that first. In both cases the scenario should publish `player_self_excluded` and then `rg_case_closed` (and the lifting fact) through the consumer.
  Resolved: `players` publishes `player_reinstated` (self_excluded → active, reason `exclusion_lifted`) when an exclusion is lifted, in spec 008's facts contract; the suppression feature now lifts through that fact, ab528e05.

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/channel/Channel.scala:108` — issue (blocking): `push_delivered` is produced for frames that were never written. `settling` writes `Delivered(r.seq, r.correlationId, r.openAt.size, now)` once each connection open at the signal has acked or closed. It counts the closed ones, and it fires even when every connection closed without acking. The common case is a dead instance: its connection is in `openAt`, never acks, expires after 90 s, and the signal is then "delivered" to 1. FR-022 (175 FR-009b) says delivered MUST mean a frame was written to a live connection, and `players` advances the message to `delivered` from this fact. Suggestion: `Leases.deliverable(after.ring).filter(_.acked.nonEmpty).map(r => Delivered(r.seq, r.correlationId, r.acked.size, now))`. Add a channel-suite case where the only connection closes or expires before acking, and check that it produces no `Delivered`.
  Resolved: `Delivered` is written only when at least one connection acked, and counts the acks; a signal settled by closes alone writes none (ChannelSuite), 6649e037.

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/consumers/Consumers.scala:44-47` and `:59-62` — issue (blocking): a redelivered fact silently loses `first_deposit_confirmed` and every identify-only send. The consumer writes the `Profile` first and claims the sends second; the two steps are not atomic. When the claims fail, the change is delivered again: `Send.start` throwing, a workflow start timing out, a restart, or a batch replay after any failure in the batch (ankka's consumers page: "a failure redelivers more than one change"). On that redelivery `Profile` answers the repeat as unchanged. `Applied` then gives `depositCountBefore == depositCountAfter == 1` and `identified = false`, so `Events.of` drops `first_deposit_confirmed` (`Events.scala:69`) and `Sends.of` drops the FR-010 identify (`Sends.scala:54`). The fact's other events are still re-derived, so nothing records the loss, which goes against SC-008. Suggestion: make what `Events` reads deterministic from the fact. The profile can remember, per deposit transaction already counted, whether it was the first (for example a `firstDepositTx: Option[String]`), and answer that on a repeat. For identify-only sends, compute `identified` against the profile as it was before that fact's group stamp, not against "changed now". Add a ConsumerTestKit case that delivers the same fact twice where the first `Send.start` throws.
  Resolved: the profile keeps its answer to each of its last 32 fact ids and replies with it to a repeat, so a redelivery derives the same events and sends, `first_deposit_confirmed` and the identify included; the consumers pass the fact id. ProfileSuite covers the repeat, the window and erasure, 749429fd.

## Should fix

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/facts/AuditPublisher.scala:49` — issue (non-blocking): configuration changes can go unaudited. `ConfigAudit` reads `ChangeSource.stateOf(Configuration)`, a key value entity, and ankka says such a consumer "sees the latest value, and intermediate values can be skipped". The record comes from `lastChange` only, so two quick `PUT`s can produce one audit record, while FR-029 asks for one per change. (`SendAudit` reads a workflow, which ankka delivers state by state, so it is not affected.) Suggestion: keep the changes as an event-sourced entity, or keep the last *n* notes in the state and have the auditor write every note newer than the last it saw.
  Resolved: the configuration keeps its last 16 change notes and `ConfigAudit` writes a record for each, by the note's id, so a skipped state loses none and a repeat is stored once (018 FR-010), de24c761.

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/api/BackofficeEndpoint.scala:126-127` — issue (non-blocking): `connections` and `webhookRefusals` describe only the instance that answered. FR-027 asks for open connections per instance, and FR-017 for refusals per brand. With three replicas each status call shows a different third. Suggestion: derive connections per instance from the `Channel` events (`Opened.instance`; a view keyed by instance, as `PresenceView` is by player). Count refusals in a small entity or view rather than an in-process `TrieMap`. Or document both as per-instance in contracts/routes.md.
  Resolved for `connections`: the presence view keeps each open connection's instance and the status sums them across the cluster (PresenceRowSuite), 709b4f2b. Declined for `webhookRefusals`: a refusal is an unauthenticated public request, and counting it durably would let anyone turn noise into writes; it stays an instance's diagnostic, which FR-017's "per brand" holds for a service that serves one brand.

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/channel/AgentChannel.scala:125-131`, `api/AgentStream.scala:65-71` — issue (non-blocking): on overflow the agent queue drops its oldest frames and keeps the connection, and the stream ignores `dropped`. FR-024 and data-model.md say the connection is dropped, as in the original's 16-frame queue. Beyond the 32-frame brand ring, frames are also lost without notice. Suggestion: end the stream when `polled.dropped > 0` (the client reconnects, as the player stream does), or record the change as a divergence in plan.md.
  Resolved: an overflowing agent queue now ends the connection with no frame, as the original's; AgentStreamSuite signals past the queue and sees the stream close, 09c2b785.

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/channel/AgentChannel.scala:136` — issue (non-blocking): `AgentChannel` (one per brand) has no `snapshotEvery`. Every agent writes `Leased` every 30 s and every login writes `Signalled`, so the journal of this one entity grows without bound and recovery replays all of it. Suggestion: `override def snapshotEvery: Option[Int] = Some(100)`, as on `Channel`.
  Resolved: `AgentChannel` snapshots every 100 events, 09c2b785.

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/EngagementService.scala` — todo: research.md (*ankka 0.16.0 and its Personal*) and plan.md's divergence row say an `ErasureHandler` runs the CRM deletion and the discards beside the erasure route, "so an erasure filed at the installation reaches the CRM too". No handler is registered anywhere in `services/engagement/src`, and `ErasureSuite` drives only the route. Under FR-016 an erasure filed at the installation would shred the keys but leave the person at Customer.io. Suggestion: register the handler, sharing `Erasure.erase`, and give it a suite case; or correct research.md and plan.md.
  Resolved: `Erasure.handler` is registered with `withErasureHandler` and runs the route's erasure for a `player/<id>` subject (another subject is not ours); a re-run deletes nothing more (ErasureSuite), 39177202.

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/send/Send.scala:202-205` with `services/players/.../facts/Facts.scala` (registration) — issue (non-blocking): whether a consented new player's `player_registered` is tracked depends on timing. `players` publishes `player_registered` and then the two registration consents. The consumer applies the registration and starts its `Send`, then applies the consents. The `Send`'s track step reads the profile only after the identify call returns, so it usually sees the consent. If the consumer stops or slows between those records, the track and the welcome transactional end `marketing_suppressed` for a player who consented. No suite covers this order: `it/Facts.player` writes the consent onto the profile directly. Suggestion: put the registration's consents on `player_registered` itself, an additive field the profile applies in the same group. Otherwise make the marketing judgement for a registration's own sends wait for that fact's consent records. Add a suite case that publishes the registration and its consents through the consumer.
  Declined: the order can only withhold a send from a player who consented, never send to one who did not, which is the fail-closed rule this spec was given; the window opens only when the consumer stops between two records of one partition. Carrying the consents on `player_registered` changes spec 008's fact and belongs to a players change; noted in research.md.

## Questions

- `services/engagement/src/main/scala/io/eitheror/casino/engagement/send/Send.scala:55-62` — question: an operator's retry allows one more attempt (`parkAt = attemptsAt(kind) + 1`). FR-025 says the retry "re-runs FR-002", which reads as four more attempts with backoff. contracts/routes.md ("the record after the attempt") agrees with the code. Which is meant? If one attempt is intended, FR-025's wording should change.
  Answered: one attempt, as contracts/routes.md and the original; FR-025 now says so (with this report).
- `services/engagement/src/main/scala/io/eitheror/casino/engagement/clients/Crm.scala:79` and `send/Send.scala:125` — question: a refusal's body (up to 500 characters) is stored as `Call.lastAnswer` in plain workflow state, not as `Personal`. Can Customer.io's 4xx bodies echo what they were sent (an invalid `to` address, an attribute value)? If they can, SC-006's dump would hold a readable address. `DumpSuite` would only catch it if its fake returned such a body. Seal the body under the player's subject, or keep only the status and an error code.
  Answered: they can (a 400 names the field it rejects). Resolved: a refusal is kept by its status only, d4334a90.
- `services/engagement/src/main/scala/io/eitheror/casino/engagement/timers/DepositDayTimer.scala:29-39` — question: the 03:05 reset pages through every player with a count above zero inside one timed-action invocation. That is two component calls per player, plus a workflow start. What bounds a timed action's run in ankka 0.16, and what happens to a brand with tens of thousands of depositors? A retry is safe (`resetDepositDay` answers false), but a player reset just before a timeout gets no identify. This is the same non-atomicity as the third blocking finding, and the same fix applies.
  Answered: ankka 0.16 sets no bound on a timed action's run; one that fails is retried for the same due time with backoff (3 s doubling to 30 s), and players already reset are not listed again. A player reset just before a failure keeps a stale daily count at Customer.io until their next fact identifies them; no send is lost. Recorded in research.md.

  Answered: the pull request's description says so.
- `services/engagement/src/main/scala/io/eitheror/casino/engagement/api/SendEndpoint.scala:95,102` — question: a send that is parked, or still trying at the 2 s bound, answers `accepted`, so `players` records the verification email as sent during a CRM outage. contracts/routes.md says so. ## Praise

Every outcome (no address, closed, suppressed per channel, fallback template, route versus fact data) can be tested without a running workflow, and the step stays a thin shell around them. The refusal order is the original's.
- `services/engagement/src/main/scala/io/eitheror/casino/engagement/send/Model.scala:71-76` and `facts/AuditPublisher.scala:17-28` — praise: each audit record comes from a note numbered and stamped by the update that made it, with an id derived from the note. A redelivered workflow state writes the same record, and later states write none. This makes at-least-once delivery safe without a deduplication store.
- `plan.md` *Divergences* — praise: each divergence names what demonstrates it. That made it possible to check claims against code, and is how the missing `ErasureHandler` was found.

## Out of scope
