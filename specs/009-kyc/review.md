# Review: 009 kyc — who a player is, shown and reviewed

**Verdict:** Request changes (before the fixes; the resolution is under each finding)
**What it does:** Adds the brand's `kyc` service. It covers the per-brand policy from a licence profile, a player's documents in the service's own bucket behind signed links, the operator's review, and the status derivation ported from `rollup.go`. It also serves the deposit and play gates that `players` and `game-provider` ask, lifetime deposits per currency, the verification window with `players`' suspend, the review queue, erasure, and the KYC facts and audit records. Alongside the service: one additive contract change (`player_kyc_pending.reason`, and the registration profile on `player_registered`), the core manifest's `kyc` entry, and the matching changes in `players` and `game-provider`.
**Should it exist:** Yes. It is spec 009's placement of KYC, which until now is spread across `casino-service`, a Go capability and five TL functions, and `players` and `game-provider` already call its gates.
**Read:** In full: every main source file under `services/kyc/src/main/` (record, policy, documents, queue, consumers, timers, clients, facts, api, `KycService`, `Settings`, `Json`, `KycCodecs`), `service.json`, `build.sbt`, the `players` and `game-provider` main-code diffs, the contract diff, `modules/core/module.json`, `contract/keys.md`, `tools/modules` main diffs, `Justfile`, `ci.yml`; spec.md, plan.md, tasks.md; research R7 and R11. Tests read: `ProfileConsumerSuite`, `LeakSuite`, `GatesLatencySuite`, `ParitySuite`, `CoverageSuite`, the head of `Parity.scala`. Skimmed: the remaining test suites by name and shape; the 41 recordings under `tests/port/kyc/` (data; checked by `CoverageSuite`); `tests/port/kyc/README.md`. Outside the diff: `CasinoPlayers.scala` and `MoneyTransactions.scala` (fact fields), `tests/port/README.md` (the `_suite` file). Not reviewed line by line: the feature bindings under `features/`, `WireTranslation.scala`, `Kit.scala`, and the remaining contracts docs.
**Size:** 187 files, +21,846 −186. About 12,000 of those lines are recordings (data). Hand-written code is about 2,800 lines of main Scala and 5,200 of tests, plus about 1,800 of docs. This is far above the size where defect-finding holds up. Because each of the 58 commits is one task and builds on the last, a split now would cost more than it saves. For the next service, split it the way the plan's build order already does: contract and manifest; pure packages and entities; endpoints and consumers; then parity.

## Blocking
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/consumers/ProfileConsumer.scala:42` — issue (blocking): the profile change is timestamped with the consumer's clock (`KycRuntime.now()`), not the fact's `occurredAt`. A redelivered `player_profile_updated` fact therefore demotes a verified player. Topics are at-least-once, so a redelivery after a rebalance or restart is expected. Suppose a player edits their address at T1 and an operator verifies at T2 > T1. A redelivery of the T1 fact (or simple consumer lag past T2) records `ProfileUpdated(at = now)` because `requiredChanged` is true (`KycRecord.scala:160-162`). `Rollup.derive` rule 1 (`Rollup.scala:111`) then sees a profile change after `verifiedAt` and moves the account to `unverified` with reason `profile_changed`. It publishes `player_kyc_rejected`, and under UKGC the next deposit and launch are refused. This happens even though the operator verified after the change. Every other consumer here is idempotent (deposits by ordinal, deadlines once, closure once); this one is not. No suite redelivers a profile fact to a verified record.
  Suggestion: pass `f.occurredAt` as the command's `at`, so `profile.changedAt` is the change's own time. Completeness is still judged against today at each derivation (`KycRecord.today(c.at)` in `derived` uses the command time, so keep `KycRuntime.now()` for that `today` if it matters). Add a `KycRecordSuite` row: a verified record, then the same `ProfileChanged` delivered twice with an `occurredAt` before `verifiedAt`; the status does not change.
  Resolved: `ProfileConsumer` and `RegistrationConsumer` pass `occurredAt`; the record's `changedAt` only moves forward and a required change already seen is not derived again; `KycRecordSuite` reads a change twice and after a later verification, 841076e

## Should fix
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/documents/Store.scala:99-103`, `api/DocumentRoutes.scala:34` — issue (non-blocking): FR-005 says the upload link "MUST allow one object of at most the brand's size limit". A presigned PUT caps nothing (research R7 says so), and nothing deletes the object of an offer that is never confirmed. `OffersDropped` drops the offer from state but leaves its object in the bucket until erasure. A player can ask for offers repeatedly; every offer is a fresh name, and a category stays unlocked until a confirm. Each offer can then hold an object of any size the store accepts. Suggestion: one of two fixes. Sign a POST policy with `content-length-range` (S3 and GCS's XML API support it; check Garage). Or have a consumer of `OffersDropped` delete the dropped offer's object, which is not a recorded document, so FR-034 is unaffected. Then amend FR-005 or R7 to say which.
  Declined: the cap stays at confirm, where the object is headed, refused over the limit and deleted; `platform/object-storage.md` describes no POST policy to cap it at the store. R7 now says so and names the unconfirmed objects, kept until erasure, as a follow-up (research Follow-ups), 6122993
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/record/KycRecord.scala:54-61` — issue (non-blocking): the lock (FR-006) is checked when an upload is offered, never when it is confirmed. Two offers for `identity_front` taken before either is confirmed can both be confirmed. That leaves two pending documents in a single-slot category: only the later counts for the derivation, but both count in "docs awaiting review", and an operator may review the superseded one. Suggestion: in `confirmUpload`, refuse `document_locked` when the category is not `other` and its latest document is pending or approved, using the same predicate as `requestUpload` (lift it into one function).
  Resolved: `confirmUpload` holds the lock with `requestUpload`'s predicate (`locked`); the endpoint deletes the refused object; record and route tests, 6122993
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/record/KycRecord.scala:56` — issue (non-blocking): a retried confirm is answered 404 `document_not_found`. The first confirm removes the offer, so a client that retries after a timeout (the player site proxies this call) is told the document does not exist when it was recorded. Suggestion: when `documentId` is already a document of the record, answer it as `withDocument` does (an idempotent confirm), not a refusal.
  Resolved: a confirm of a recorded document writes nothing and answers as the first; `DocumentsSuite` compares the two answers, 6122993
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/Settings.scala:25,40`, `services/kyc/README.md:62` — issue (non-blocking): `KYC_SUSPEND_RETRY` is parsed, validated and documented as "the wait before the window's suspend is asked again", but nothing reads `suspendRetry`. `WindowTimer` throws and the timer runtime's own backoff decides the wait. Suggestion: delete the setting and its README row, or make `WindowTimer` use it, and say which in R10.
  Resolved: the setting, its README row and the kit's value are removed; R10 already names the timer's backoff as the retry, 9eb602a
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/record/Gates.scala:37-38` — issue (non-blocking): `DEPOSIT_BLOCKED_KYC_CURRENCY` refuses a verified player too, as FR-019 requires, but the message says "until your account is verified". A verified player depositing in another currency is told to do something they have already done, and nothing they can do lifts the refusal. Suggestion: a message that does not hang on verification, for example "Deposits are accepted in <currency> only". Then the `gates.feature` row, if it quotes the text.
  Resolved: "Deposits in this currency are not accepted"; no feature quotes the text; research's table updated, 441e296
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/KycService.scala:47-48` — issue (non-blocking): `PolicyFlagger`'s searches stop at 10,000 rows, silently. FR-022 says "every" player over a lowered threshold is flagged. On a large brand the players past the first 10,000 by `row_key` are never flagged, and nothing logs it. Suggestion: page through `overThreshold` and `overSof` (by `row_key` after the last seen) until a page comes back short. (if-minor) The same cap at `OperatorEndpoint.scala:77-78` makes `sort=newest` the newest of the oldest 1,000. Order the query by the direction asked instead of reversing the capped rows.
  Resolved: the searches page by `row_key` after the last seen, 1,000 at a time; each queue filter has a newest-first query, so `sort=newest` is the newest 1,000; `QueueSuite` runs the searches over Postgres, ebfb236
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/documents/Store.scala:68-87` — suggestion (non-blocking, if-minor): the S3 client sets no `apiCallTimeout` or `apiCallAttemptTimeout`. A store that accepts the connection and then stalls holds a request thread on upload, confirm, view and erasure for the SDK's socket default. Suggestion: set both in `ClientOverrideConfiguration`, a few seconds each, so a stall is answered `503 storage_unavailable` promptly.
  Resolved: a 5-second attempt timeout and a 15-second call timeout, 9eb602a

## Questions
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/consumers/ProfileConsumer.scala:28` (`Read.from`, `StartFrom.Latest`) — question: what happens to the players a brand already has when `kyc` is first deployed after `players` and `wallet`, as on the kind brand now? Their registrations, profiles and deposits are never read. These players have no deadline, an incomplete profile (so `PUT /status verified` is refused `profile_incomplete` and automatic verification stays `pending`), and lifetime deposits of zero until the next fact. Spec 019's opening event covers Spinvibe; does anything cover a brand that ran `players` before `kyc`? Either answer settles it: "019 or an opening run covers every such brand", or `StartFrom.Earliest` for these three topics. With the blocking fix above, every consumer here is idempotent on replay.
  Answered: `kyc` is in `core` with `players`, so a brand gets both from its first apply; the one population that predates it is Spinvibe's, which 019's opening events cover. The kind brand is a test brand. `StartFrom.Earliest` would be wrong besides: replaying old registrations sets deadlines already past, and their timers would suspend at once
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/record/KycRecord.scala:184` — question: should a player whose documents are `pending` be suspended when the window lapses? The code acts on any status but `verified`. FR-025 and `window.feature` say "a player still unverified", and this spec uses `unverified` as a status of its own. A UKGC player who uploaded on day 2 and is waiting on the compliance team would be suspended on day 3. If that is intended, write "not verified" in FR-025 and add a pending row to `window.feature`. If not, restrict the lapse to `Unverified`.
  Answered: intended. The original's expiry check fires on `kyc_status != "verified"` (`tl/compiler/testdata/fixtures/casino_player_kyc_window_expiry_check.tl`), so pending players are included; FR-025 now says "not verified (unverified or pending)"
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/KycService.scala:63-69` — question: what happens to events the consumers receive between `start` and `started`? `KycRuntime.timers` and `.queue` are wired only after the service has started, so `RecordTimers` or `PolicyFlagger` handling an event in that gap throws "not wired". If ankka's consumer retries a throwing handler from the same offset, this is harmless. If it skips the event, a deadline's timer is lost. Wiring before `start`, or a note on which behaviour ankka 0.13 has, settles it.
  Answered: harmless. A handler that throws does not advance and the change is delivered again (ankka `docs/build/consumers.md:71`), so an event in the gap is handled once the service is wired
- `services/kyc/src/main/scala/io/eitheror/casino/kyc/consumers/ProfileConsumer.scala:21-25` — thought: the lenient read skips an unreadable `deposit_confirmed` and logs it.
