# Review: spec 018, the shared audit (a0f13277...HEAD)

**Verdict:** Request changes
**What it does:** Adds `services/audit`, the one service of the shared `reasoner` project. It consumes each brand's `platform.audit` and `platform.modules` and `payments`' `platform.audit` as bytes. It keeps action records and passes over unattended money events, replaces people's ids with registry pseudonyms, and stores each record once in a key value entity with a view. It serves queries, exports, re-identification, role grants, retention and status, and records each of them. The change also amends the contract (`Routes`, `Layout`), the realm, the modules tool, both shared manifests, and the audit mappings of `wallet`, `players` and `responsible-gambling`.
**Should it exist:** yes. Specs 001 and 002–011 all write `platform.audit` and nothing reads it outside the brand. This is the reader spec 001 FR-016/FR-018 reserves for `reasoner`. Its shape (consumer per source, pure `Keep`/`Stored`, registry keyed by HMAC) is the plan's and fits the repository's service pattern.
**Read:** spec.md, plan.md, tasks.md, data-model.md, contracts/{routes,ingest,recording}.md, research.md (R8, *Found during implementation*), PERF.md. Read in full: every main source under `services/audit/src/main`, the `Routes`, `Layout`, `Manifest`, `Realm` and `Render` hunks, both manifests, CI and Justfile hunks, and the `wallet`, `players` and `responsible-gambling` main hunks. Tests read in full: `LeakSuite`, `StoredSuite`, `ReidentifySuite`, `RoutesSuite` hunk, players' `PublishersSuite` hunk. The other suites were skimmed for shape, sleeps and ports. Code opened outside the diff: `contract/.../personal/Personal.scala` (`PersonalFields.names`), `PlayerEntity` `Erased` handler and consent commands, wallet `AccountFacts`/`AccountState`, and ankka's workflow skill (timers are a cluster singleton). Not reviewed line by line: the feature bindings beyond their ignore lists, `IngestPerf`, spec prose beyond the requirements.
**Size:** 139 files, +7,617 −127 (about 5,900 Scala, 1,700 docs). That is well past where defect-finding holds up. The repository builds a spec per branch, so a split is not demanded. The neighbour changes (wallet, players, responsible-gambling mappings and their tests, ~550 lines) were separable and would have been reviewable on their own ahead of the service.

## Blocking

- `contract/src/main/scala/io/eitheror/casino/contract/access/Routes.scala:219-223`, `services/audit/src/main/scala/io/eitheror/casino/audit/api/RolesEndpoint.scala:56-71`, `services/audit/src/main/scala/io/eitheror/casino/audit/roles/Grants.scala:24-25`. Issue (blocking): the realm cannot express "compliance officer of brand A only". `auditScope` admits every `brand_<slug>` a person holds once they hold the global `brand_compliance`. Two consequences follow, both against FR-013 ("a role for one brand MUST be refused another brand") and FR-016. (a) Granting `brand_compliance` for A to someone who is already an operator of C (`brand_C`) gives them C's whole audit. (b) Revoking A from an officer of A and B keeps `brand_compliance` (since B remains) and keeps `brand_A` (deliberately, line 55's comment). Their scope is still {A, B}, yet the route answers `revoked` and writes an `audit.role-revoke` record. The audit then holds a record that is false. The grant also hands out `brand_A`, the brand's operator role, so a compliance grant makes the person an operator of A in every other service. Suggestion: a per-brand compliance role made by `Realm.ensure` beside `reidentify_<slug>`, say `compliance_<slug>`. `auditScope` reads only those roles, a grant assigns that role alone, and a revoke removes exactly it. Add a `RolesSuite` case with an officer of two brands, revoke one, and assert the records route refuses that brand. Research R8 and contracts/routes.md change with it.
  Resolved: `compliance_<slug>` per brand made by `Realm.ensure`; `auditScope` and `reidentifies` read only it; a grant assigns and a revoke removes exactly the role named; `RolesSuite` revokes one brand of a two-brand officer and that brand is refused; R8 and routes.md amended, 228cda43

- `services/audit/src/main/scala/io/eitheror/casino/audit/AuditService.scala:63-66`, `services/audit/src/main/scala/io/eitheror/casino/audit/registry/RegistryKey.scala:58-71`, `services/audit/src/main/scala/io/eitheror/casino/audit/Wiring.scala:22-25`. Issue (blocking): the keys reach ingest and the routes only through `Wiring.keys`, a JVM-local reference, and only the `seed` timed action sets it. ankka runs timers from a cluster singleton sweeper (ankka-workflows rule 5), so the seed runs on one node. With more than one replica, every other node's consumers throw `IllegalStateException` on every message, forever. Their routes answer 500 from `Wiring.requiredKeys`. Nothing in `service.json` or `shared/reasoner/manifest.json` pins the service to one replica, and no suite starts two nodes. Suggestion: read (and, at first start, make) the keys on each node as it starts, through the started service's secret store, before `AuditService.started`. Keep the seed only for making the keys. If one replica is a deliberate constraint, declare it in the descriptor and say why in the README. Either way, add a kit case with two nodes, or say why the kit cannot have one.
  Resolved: every node reads the keys from its own secret store (`Wiring.keysFrom(context.secrets)` in the consumers, `clients.secrets` in the routes); the seed only makes them; `RegistryKeySuite` covers a node that never ran the seed, 0f5a1448

- `services/players/src/main/scala/io/eitheror/casino/players/facts/Facts.scala:165-166`. Issue (blocking): a player's consent change is recorded as `change(e.channel, …)`. The channel for email consent is `"email"` (`PlayerEntity.scala:268`), which is in `PersonalFields.names`, and the change carries `before`/`after` values ("false"/"true"). `Ingest.carriesPersonalValue` therefore quarantines every player email-consent record as `personal_value` (`Ingest.scala:55`), and the action never reaches the shared store. FR-004 lists consent as an audited player action. The operator case at line 178 has the same shape and predates this diff, but this diff is what makes it a quarantine. No test covers consent: players' `PublishersSuite` covers close and profile edit only. Suggestion: name the field after the consent, not the channel, for both cases: `change(s"consent.${e.channel}", …)` or `emailConsent`/`smsConsent`. Add a mapping test asserting that no `playerAudit` output carries a value on a field in `PersonalFields.names`, the check the erasure mapping already has.
  Resolved: both consent cases record `consent.<channel>`; `AuditMappingSuite` asserts no player audit output carries a value on a personal field, ad648569

- `services/audit/src/main/scala/io/eitheror/casino/audit/api/IdentitiesEndpoint.scala:50-57,59-69`. Issue (blocking): `/who` writes the caller's raw `pseudonym` as the record's `subject` and the raw `reasonCode` as a `reason` change. It does so on every path, including an unknown pseudonym and a refusal, and the route is open to any staff member (`Routes.staffMember`). An officer who pastes a player's real id where a pseudonym belongs gets it stored, permanently, in an append-only store. That breaks SC-002 and FR-008 ("nothing the shared audit … writes … holds a real id"), with no repair path short of the retention sweep. Any member of staff can also write arbitrary, unbounded text into records nobody may change or delete. The same applies to `reasonCode` on `/pseudonym`. Suggestion: refuse a `reasonCode` that is not a code (e.g. `[a-z0-9_]{1,64}`). For a pseudonym the registry does not hold, record its digest (`Ids.digest(key, Own.Installation, raw)`), never the text. Validate a known pseudonym's shape (a UUID) before recording it as given. Add a `LeakSuite` case that posts a real id to `/who` and searches the store.
  Resolved: a `reasonCode` is `[a-z0-9_.-]{1,64}` or 400 unrecorded; an unknown pseudonym is recorded as its digest; `ReidentifySuite` and `LeakSuite` post a real id to `/who` and search, 0580411e, dd26213e

## Should fix

- `services/audit/src/main/scala/io/eitheror/casino/audit/api/StatusEndpoint.scala:53`. Issue (non-blocking): `lagSeconds` is `now − lastReceived`, the time since the last message arrived, not lag. A consumer an hour behind but busy reports 0, and a quiet, up-to-date source reports a growing number. FR-007 and FR-024 ask for the lag, and SC-003 is stated in it. Suggestion: report `lastReceived − lastOccurred` (how far behind the newest record processed was). Either keep "since last record" as its own field (`idleSeconds`) or drop it, since `lastReceived` already says it.
  Resolved: `lagSeconds` is `lastReceived − lastOccurred`; `lastReceived` already says the idle time, so no second field, f32f89af

- `services/audit/src/main/scala/io/eitheror/casino/audit/api/StatusEndpoint.scala:62-64`. Issue (non-blocking): `topicKeeps` is the constant `"everything"`. FR-022 asks the service to report any brand whose topic no longer reaches the restore point, naming the first time it can reach. A literal cannot report that, and the status will claim "everything" on a brand whose topic was declared shorter. Suggestion: derive it from the brand's manifest retention, rendered into the env as `AUDIT_BRANDS` is. Or answer "not stated" until it can be, as the installation sources do.
  Resolved: "not stated" until a brand's topic retention reaches the service, in routes.md and the README, f32f89af

- `services/audit/src/main/scala/io/eitheror/casino/audit/own/Own.scala:34`, `services/audit/src/main/scala/io/eitheror/casino/audit/api/ExportsEndpoint.scala:81-90`, `services/audit/src/main/scala/io/eitheror/casino/audit/exports/Export.scala:79-82`. Issue (non-blocking): every record of the audit's own gets a random UUID id, so a retry makes a second record. Two cases: (a) `writeStep` writes the completion record and then calls `ExportFormat.exported`; if that call or the state update fails, the step is retried (`maxRetries(2)`) and writes another completion record. (b) Two concurrent `POST /v1/audit-exports` with one key both read `!started` and both write a request record. The spec's edge case says an export is "recorded once at request and once at completion". Suggestion: give `Own.record` an id the caller derives (`export/<key>/requested`, `export/<key>/completed`, `sweep/<id>`), so a repeat is `Record.Same`. In `start`, write the request record only when `Export.start` reports that this call started it.
  Resolved: `Own.record` takes a caller's id; an export's records are `export/<key>/<stage>` and a sweep's `sweep/<id>`, so a retried step or a second request is `Same`; `ExportSuite` covers it, bb0938c5

- `services/audit/src/main/scala/io/eitheror/casino/audit/api/RolesEndpoint.scala:80-85`. Issue (non-blocking): `GET /v1/audit-roles/{role}` answers each holder by realm user id. Suggestion: answer the installation pseudonym (`Grants.holder`). If the owner needs realm ids to act, write the exception into SC-002 and the glossary rather than leave the property false.

Question: `other` digests any change value that contains a named person's real id as a substring, and `amount` is read after that. - `services/audit/src/main/scala/io/eitheror/casino/audit/ingest/Ingest.scala:57`. Thought: skew counts only an occurrence ahead of arrival. A writer whose clock runs slow looks the same as backlog, which is probably the right call, but the edge case reads "a difference above a bound".
  Answered: deliberate. A slow writer's records look like backlog, which `lagSeconds` reports; only an occurrence ahead of arrival is a clock fault the bound can tell.
