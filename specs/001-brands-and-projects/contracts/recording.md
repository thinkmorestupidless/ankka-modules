# Contract: recordings and parity tests (the port method)

## Layout

```text
tests/
├── port/<service>/<scenario>.json       # one recording per Go test function
├── port/<service>/suite-result.json     # the original's own suite result for that run
├── stubs/<psp>/                         # Go stubs: health at GET /healthz
└── original/
    ├── compose.override.yml             # the original's stack plus the seven stubs
    └── e2e-recording.patch              # the RoundTripper added to tests/e2e's client
```

`<service>` is the rebuilt service the recording establishes requirements for (`wallet`,
`game-provider`, `merchant`, ...). A scenario that spans services is filed under the one it enters.

## A recording

```json
{
  "scenario": "TestScenario07_BetWinRollback",
  "requirement": "002/FR-014",
  "recorded_at": "2026-10-20T10:12:03Z",
  "original": {"commit": "b7f0e9d0", "brand": "spinvibe"},
  "steps": [
    {
      "name": "place bet",
      "request": {"method": "POST", "path": "/v1/casino/brands/{brand}/wallets/{player}/EUR/bets",
                  "headers": {"Content-Type": "application/json"}, "body": {"amount": 1050, "round_id": "r1"}},
      "response": {"status": 200, "body": {"balance": "98.50", "transaction_id": "..."}},
      "capture": {"bet": "$.transaction_id"},
      "vary": {"$.transaction_id": "generated by the original"}
    }
  ],
  "outbound": [
    {"stub": "fake-st8", "request": {"method": "POST", "path": "/api/operator/v1/..."}, "response": {"status": 200}}
  ]
}
```

Rules (ankka-port, FR-030):
- Each scenario runs twice on fresh ids; a field that differs between runs goes under its step's
  `vary` with its reason and is checked for presence only, in that step alone. Nothing is added to
  `vary` to make a rebuild pass. A recording-wide `vary` (recordings merged before 2026-10-18) holds
  in every step; `$` there makes every answer vacuous, so such a recording is re-merged.
- A step named `setup:`, `observe:` or `time:` is arranged: it is sent and its captures taken, and
  its answer is not compared.
- `{name}` placeholders in later paths and bodies are filled from `capture`.
- Every outbound call goes to a stub; what was sent is recorded. Recording refuses to start while
  a provider the original calls has no stub answering `/healthz` (FR-029).
- Time-driven behaviour is driven by the original's clock or config; without one, the requirement
  is marked `inspected` in the service spec, not recorded.
- Amounts in a recording are as the original answers them (decimal strings on the wallet API);
  the rebuild answers the same wire format and refuses decimals only on input (FR-026).

## A parity test

- One test per recording, in the service's own test kit (`AnkkaTestKit.start`), named after the
  scenario: `TestScenario07_BetWinRollback` → `test("TestScenario07_BetWinRollback")`.
- Replays the steps with captures substituted, compares each response's status and body field by
  field, `vary` fields for presence only, and fails with the recording's path and the first
  differing JSON path: `tests/port/wallet/TestScenario07_BetWinRollback.json $.steps[2].response.body.balance`.
- Written to fail first and broken once on purpose. Never calls the original. A test blocked by a
  listed divergence (read-after-write through a view, HTTP/1.1 only, a transaction become a
  workflow) is marked with that divergence, not deleted.
- Every service spec lists the recordings it names under *Established by*; SC-006 checks each exists.
