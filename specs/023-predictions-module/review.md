# Review: the predictions module — markets and an exchange in a brand (spec 023, main...HEAD)

**Verdict:** Request changes
**What it does:** It adds two ankka 0.14.2 services, `markets` and `exchange`, built on ankka-predictions' components. They supply the gate, ledger and resolution ports from the brand's `players`, `kyc`, `responsible-gambling` and `wallet` and from the operator roles. It adds the four predictions topics to the contract (with nested fact objects), a `predictions` module manifest, erasure wiring through a new `erasure-targets` value, a settlement retry workflow, a daily reconciliation against `money.transactions`, and the player reads and price stream.
**Should it exist:** Yes. Decision 0055 puts the prediction market here, and the shape (ports in the consumer, every rule in the library) follows the spec and the libraries' design. Nothing here duplicates an existing mechanism.
**Read:** in full: every main source of both services (`api/`, `ports/`, `retry/`, `reconcile/`, `reads/`, `facts/`, `terms/`, `erasure/`, the runtimes and settings), the contract diff (`Routes`, `FieldType`, `Fact`, `Compatibility`, `Markets`, `Exchange`, `Topics` and their suites), the modules-tool diff, the `players`/`kyc`/`responsible-gambling` diffs, `modules/predictions/module.json`, `contract/keys.md`, spec.md, plan.md, tasks.md, research.md, contracts/, data-model.md, quickstart.md. Tests: `LedgerSuite`, `SettlementFeatures`, `NoRulesSuite`, the kubectl part of `PredictionsOnKindSuite`; the other suites skimmed for structure, sleeps and ports. Generated JSON schemas under `contract/schemas/` skimmed only. Outside the diff: ankka-predictions' `Settlement.scala`, `Ports.scala` and `Placement.scala` (branch 005-player-commands-at-the-book), `responsible-gambling`'s `Checks.scala` and may-bet route, game-provider's `Neighbours.mayBet`, `.github/workflows/ci.yml` and `release.yml`, ankka's component-client docs (blocking `invoke`).
**Size:** 146 files, +8,158 −121 (about 5,800 lines of Scala). Above the 1,000-line split threshold. A spec-kit feature branch lands whole by this repository's habit, so this review does not block on size. The split that would have reviewed best is (1) the contract's nested facts, the four topics and `Routes.operatorHolding`, (2) `erasure-targets` in players and the modules tool, (3) `markets`, (4) `exchange`. Defect-finding over a diff this size is weaker than usual, so the money paths (`ports/`, `retry/`, `reconcile/`) got the closest read.

## Blocking

- `services/exchange/src/main/scala/io/eitheror/casino/exchange/ports/Ledger.scala:31-35,66-68` — issue (blocking): in a split or merge trade, a leg the wallet refuses stops the trade at that leg. Every later leg is never sent, and nothing will ever send it. `Ledger.each` returns at the first leg that is not `Done`. `kept` starts a `SettlementRetry` for that one call only. The library's settlement consumer then logs the refusal and passes the event (`Settlement.scala:43-51`). So in a split where the first buyer's charge is refused, every other buyer gets the position, their reservation is never charged into the pool and never released, and the pool is short at payout. The comment on `each` ("a retry repeats the done ones under their keys") describes behaviour the retry does not have: it repeats one `WalletCall`. `LedgerSuite.scala:85-95` asserts this behaviour (`s.calls.size == 1`, only `m1/t4/ada` handed to the retry), so the suite is green on the defect. The daily reconciliation would flag it a day later, but FR-003 says a refused settlement is "recorded, retried and raised", and here it is neither recorded nor retried.
  Suggestion: send every leg and hand each refused leg to its own retry (each already has its own key, `Ledger.key`). Then answer the first refusal:
  ```scala
  def each(legs: Vector[Leg])(call: Leg => LedgerAnswer): LedgerAnswer =
    val answers = legs.map(call)            // every leg is sent; `kept` starts a retry per refused leg
    answers.find(_ != LedgerAnswer.Done).getOrElse(LedgerAnswer.Done)
  ```
  Change the test so both legs are called and both refusals are handed over. Add a case where the first leg is refused and the second is done.
  Resolved: `Ledger.each` sends every leg and a refused leg starts its own retry under its own key; LedgerSuite has the both-refused case and the first-refused, second-done case, 2cb56ed.

- `services/exchange/build.sbt:12`, `services/markets/build.sbt:10`, `.github/workflows/release.yml:24` — issue (blocking): neither service resolves its ankka-predictions dependency outside this machine. `exchange` pins `0.1.1`, which has no tag (ankka-predictions' only tag is `v0.1.0`, and research.md says 0.1.1 "waits on Trevor's tag"). `markets` pins `0.1.0`, which research.md says is not on Maven Central because its signing failed. Both resolve only from `~/.ivy2/local`. The release workflow builds an image for every `services/*/build.sbt`, and the manifests job needs the images job. So the first `v*` tag after this merges fails and publishes no module, core included. Merging this also leaves `main` unbuildable for these two services on any clean checkout.
  Suggestion: publish ankka-predictions 0.1.1 (both components) where the release runner can resolve it, pin both services to that release, and say in the build comment where it resolves from. If the merge cannot wait for that, the next option is keeping the two services out of the release matrix until it exists, which is worse because the manifest then names unbuilt services.
  Resolved: both services pin ankka-predictions 0.1.1 (owners' commands at the book's time, ankka-predictions#6, and the market's own clock, #7, both merged), b32775f. The release itself waits on the v0.1.1 tag, which is Trevor's; until it is published to Maven Central, CI's markets and exchange jobs cannot resolve it, and the pull request says so.

## Should fix

- `.github/workflows/ci.yml` — todo: CI has no job for `markets` or `exchange`, and no path filter names them. Every other service has both. As it stands, nothing in CI runs the suites that hold the ledger and gate mappings (and they need a resolvable library, see above). - `services/markets/src/main/scala/io/eitheror/casino/markets/api/OperatorEndpoint.scala:36-42,53-57` — issue (non-blocking): the draft and change routes write `MarketTerms` before the library has accepted the command, and `markets`' terms are not write-once. A refused command therefore still replaces the market's limits. Example: a `POST /drafts` under the id of an approved market is refused by the library as `state`, but the approved market now opens with the limits from that refused body. No fact records the change, since the limits are on no `markets.events` family. A `change` that omits both limits also resets drafted limits to the brand's defaults. Suggestion: write the terms only after the library's answer is `Right` (the draft and change are what make the market's terms current), and decide whether an omitted limit on `change` keeps the drafted one. The limits are a regulatory figure (the DCM position limit, per the Assumptions), so consider carrying them on `market_drafted`/`market_changed`.
  Resolved: the terms are written only once the library takes the draft or the change, and a change that leaves out a limit keeps the drafted one; two LifecycleItSuite cases, 6c60d20. Declined (limits on `market_drafted`/`market_changed`): a new field on a fact is a contract change outside contracts/facts.md; noted for the pull request as a follow-up.

- `services/markets/src/main/scala/io/eitheror/casino/markets/Settings.scala:31-33`, `services/exchange/src/main/scala/io/eitheror/casino/exchange/api/ServiceEndpoint.scala:70-76` — issue (non-blocking): `markets` accepts `predictions-taker-fee-bps` from 0 to 10,000 and sends it as `takerFeeBps`, but `exchange` never reads the field. The library on 0.1.x has no fee. A brand that sets a rate believes it charges a fee and charges nothing, with no warning. Suggestion: until ankka-predictions spec 007 lands, refuse any rate above 0 at start (`PREDICTIONS_TAKER_FEE_BPS: the taker fee waits on ankka-predictions 0.2.0`), the way R8 already treats the fee scenarios.
  Resolved: a rate above 0 stops markets at start naming ankka-predictions 0.2.0; SettingsSuite, f97a61e.

- `services/exchange/src/main/scala/io/eitheror/casino/exchange/api/ServiceEndpoint.scala:21-22`, `services/markets/src/main/scala/io/eitheror/casino/markets/drive/ExchangeDriver.scala:32` — issue (non-blocking): the route's doc says a redelivered command is refused "as `state` or `out of order`, which `markets` takes as done". `ExchangeCalls.send` takes only `409 state` as done, so a redelivered `suspend` or `close` the book refuses as `out of order` writes a refusal record on `platform.audit` for an event that was in fact applied. Suggestion: treat `409 out of order` as done too, or correct the comment if audit noise on redelivery is intended.
  Resolved: the comment is corrected (fde695f), and `out of order` is still raised, not taken as done: it was a real defect in the library, not redelivery noise. Owners' orders moved the book's clock, so a suspend, close or finalise made a moment before them was refused and the book traded on. ankka-predictions#7 (4c791b5) orders a market's commands by the market's own clock; a redelivered command it applied is `state`, taken as done; `out of order` now means a command older than the market's last, a fault worth the audit record. Test through the route, 1b2b4fb.

- `services/exchange/src/main/scala/io/eitheror/casino/exchange/reconcile/Tally.scala:23-31` — issue (non-blocking): one key-value `Tally` per market holds every wallet transaction id ever seen (`transactions`), every refused order (`refused`), and a sum per order, release and trade key. All of it is rewritten on every exchange event and every wallet fact for the market. State and write cost grow with the market's trade count, which makes the total work quadratic over a busy market's life and eventually hits the state size limit. Suggestion: key the dedupe by the fact itself (one small entity or view row per transaction id or sequence), and keep in the tally only per-family totals plus the open keys, or the differences. The exchange side is already deduped by `exchangeSeq` and needs no set.
  Resolved: each key is its own entity (its two sums and the sources that moved it, each counted once in one write), a view lists a market's unbalanced keys, and the check reads it; ReconcileItSuite and TallySuite updated, 88f4896.

- `services/exchange/src/main/scala/io/eitheror/casino/exchange/api/PlayerEndpoint.scala:61-69` — issue (non-blocking): each SSE subscriber runs its own `Source.tick` every 250 ms. Each tick makes 2 + N blocking `invoke` calls (prices, terms, one depth per outcome) inside a stream `map`. ankka's docs ("Blocking is free") cover endpoints, steps, consumers and timed actions on virtual threads, not stream stages, so these calls probably block the stream dispatcher. The load grows with subscribers × outcomes × 4 per second whether or not the book moved. Not run under load; the dispatcher question needs a run or the ankka docs to settle. Suggestion: `mapAsync(1)` over `invokeAsync`, or one shared source per market (`BroadcastHub`) fed from the book's sequence, so subscribers share one poll.
  Resolved: each tick composes `invokeAsync` calls under `mapAsync(1)`, and a book's known terms come from the instance, so no stream stage blocks, a64238e. One poll per subscriber remains; a shared source per market waits on a load figure that shows the need.

- `services/exchange/src/main/scala/io/eitheror/casino/exchange/ports/Neighbours.scala:54` — suggestion (if-minor): `may-bet`'s decisions are `allowed`, `excluded`, `cooling_off`, `spending_limit` and `unavailable` (`rg/profile/Checks.scala:43-48`). `locked`, copied from game-provider, is not one of them. `spending_limit` falls into `Unavailable`, so once spec 010's amendment folds losses into may-bet, an over-limit order is refused `bet gate: unavailable` instead of naming the limit as FR-002 asks. Map `spending_limit` (and RG's own `unavailable`) explicitly.
  Resolved: `spending_limit` refuses naming it, RG's `unavailable` is mapped explicitly, `locked` is gone; GatesSuite cases, fde695f.

## Questions

- `services/exchange/src/main/scala/io/eitheror/casino/exchange/ports/Ledger.scala:17-19` — question: a `release` the wallet refuses (for example `RESERVATION_NOT_FOUND`) is neither retried nor audited. The library logs it and passes the event, which leaves the player's money held. FR-003 names only settlements for the retry. Is a refused release meant to surface only through the daily reconciliation? If yes, say so in R5. If not, give release the same `kept` path.
  Answered: yes, a refused release surfaces through the reconciliation, as a difference on its `release` key; R5 now says so (10ae6ed). FR-003 names settlements, and a release refused as `RESERVATION_NOT_FOUND` has nothing to retry against.
- `services/exchange/src/main/scala/io/eitheror/casino/exchange/reconcile/Consumers.scala:82-86` — question: `WalletTally` throws for any reservation or settlement fact whose order or trade the exchange has not indexed, so the topic redelivers it. Today only `exchange` calls those routes, so the throw is transient. When another service (spec 024's pool, say) reserves through the wallet, its facts are never indexed here, and the consumer stops on them for good. Should an unknown id be skipped after a bound, or should the wallet facts carry which caller made them?
  Answered: today only exchange makes those wallet calls, so the throw is transient. R12 now records the constraint for spec 024: a service that reserves or settles through the wallet must index its own ids or carry the market on the fact (10ae6ed).
- `services/exchange/src/main/scala/io/eitheror/casino/exchange/reconcile/Consumers.scala:33-34` — thought: the daily check compares the two sides while trading is live, so a trade whose wallet fact is still in flight at the check is reported as a difference. Expect occasional false records on busy markets. Checking only keys older than the last check, or re-checking a difference once before raising it, would quiet that.
  Answered: expected and accepted. A daily record is marked `check: daily`, and the final check, ten minutes after finality, is the one that stands; R12 says so (10ae6ed).
- `contract/keys.md:124-130` — question: through a vendor, a brand running `predictions` must write `erasure-targets` by hand until spec 021 renders it. If it forgets, players never asks `exchange`, and an erased player's resting orders stay on the book holding their reservation. Is there a check (the modules tool's validate, or the kind suite) that refuses a brand entitled to `predictions` whose values omit it?
  Answered: locally, the modules tool renders `erasure-targets` from the planned modules' erasure route rows when the brand's values leave it out (`Render.erasureTargets`), so a brand on kind needs nothing by hand. Through the vendor nothing refuses the omission until spec 021 has the vendor render it, as keys.md says; that gap is spec 021's.
- `services/exchange/src/test/scala/io/eitheror/casino/exchange/NoRulesSuite.scala:27-28` — thought: SC-001's check exempts `api/` and `ports/`, which is where every domain command is built. So it guards the directories least likely to grow a rule. Narrowing the exemption to the specific constructors the routes need would make it a real guard.
  Answered: `api/` and `ports/` build the library's commands from requests and neighbours' answers. A list of permitted constructors would change with every route, and a rule written as a constructor call would pass it, so it would guard no better. The review is the guard there, and SC-001's check covers the directories where a rule would hide in a component.
