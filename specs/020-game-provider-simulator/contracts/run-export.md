# Contract: a run exported as a recording (FR-021)

`GET /v1/simulator/brands/{brand}/runs/{runId}/export` answers one document in the shape spec 001's
recording contract defines (`specs/001-brands-and-projects/contracts/recording.md`), so the brand's
test kit replays it with `contract.port.Recording.load` and `Replay.run` without edits (SC-006).

## Mapping

| Recording field | From the run |
|---|---|
| `scenario` | `sim-<scenario name>-<runId>`; a load run is `sim-load-<profileId>` |
| `requirement` | `020/<scenario name>`; the scenario's `source` is carried in `original.source` |
| `recorded_at` | the first attempt's `sentAt` |
| `original` | `{"simulator": "<version>", "brand": "<slug>", "source": "<scenario.source>"}` |
| `runs` | `1` |
| `steps[]` | one per **answered attempt**, in `sentAt` order: `name` = `<step>/<callback>#<attempt>` (or `<callback>#<attempt>` in the default scenario); `request` = method `POST`, the callback's route, headers `Content-Type` and `x-st8-sign`, the body as sent; `response` = the HTTP status and the body as answered, personal fields of a profile redacted |
| `capture` | `{"wallet_token": "$.token"}` on a `check` step, so later steps fill `{wallet_token}` |
| `vary` | `$.steps[*].request.headers.x-st8-sign` ("random nonce"), every `transaction_id`, `cancel_id` and `round` the simulator generated ("generated by the simulator"), `$.steps[*].response.body.balance` **only** when the scenario's expectation is not `exact` ("depends on the player's balance at replay") |
| `outbound` | empty: the simulator is the outside caller |

A `malformed_body` attempt is a step whose `request.body` is the raw text and whose response is the
400; an attempt with no answer (timeout, unreachable) is **not** a step: a recording replays what
was answered. The run's verdict is not part of the recording; `GET .../verdict` carries it.

## Replay

The brand's parity test replays the export against the brand's provider routes, re-signing each
step's body with the kit's own key (the `x-st8-sign` value varies), substituting captured values,
and comparing status and body field by field as `Replay.run` does. A step whose answer depended on
a balance the replaying brand does not have (a `not_enough_money` on a fresh wallet, for instance)
is the scenario author's problem: the expectation must be stated as `exact` only when the scenario
sets the balance itself, else the balance varies.
