# Review: spec 031, every service on ankka 0.18.0 and the player clients generated from service descriptions (`origin/main...HEAD`)

**Verdict:** Approve with comments (the six under "Should fix" are expected before merge or answered with a reason; none is a defect in what the services answer)
**What it does:** Moves the contract, the modules tool and all 21 services to ankka 0.18.0 and makes the modules tool refuse a runtime the installation's platform cannot run. Then nine services describe their 79 player routes, keep the description (`openapi.player.json`) under a CI check and a check against the original's recordings, and the player SDK's route tables and wire shapes are generated from those descriptions, leaving the module clients as hand-written mappings.
**Should it exist:** yes, because the SDK's routes and parsers were a second, hand-kept copy of what the services answer, and nothing failed when the two drifted; after this a route that changes fails its service's job and a description that changes fails the SDK's. One ankka version is a precondition (`described` and `HeldToDocument` are 0.18.0's) and a platform runs only its own minor version and the one below.
**Read:** In full: `contract/` main and test additions (`http/Json.scala`, `port/DescriptionCheck.scala`, `port/HeldToPlayerRoutes.scala`, their suites, `DescriptionFeatures`), `build.sbt`, `.github/workflows/ci.yml`, `Justfile`, `scripts/describe-diff.py`, the modules tool (`Runtimes.scala`, the `Main.scala` call sites, `RuntimesSuite`, `PlatformVersionFeatures`, `Fixtures`), the main diffs of all nine described services (`Described.scala`, the described endpoints, `Answers`), the `port/DescriptionSuite.scala` of players, kyc, rewards, game-provider, wallet and responsible-gambling, `HeldFixtureSuite`, `sdk/player/scripts/generate.ts`, the four `client.ts`, `selection.ts`, both `events.ts`, `engagement/inbox.ts`, `src/testing/doubles.ts`, `eslint.config.js`, `tests/unit/generate.test.ts`, `tests/features/generated-clients.steps.ts`, and `spec.md`, `plan.md`, `tasks.md`, `research.md`, `contracts/description-check.md`, `contracts/runtime-check.md`. Sampled, as generated: `services/*/openapi.player.json`, `sdk/player/src/*/routes.ts`, `sdk/player/src/*/shapes.ts` (core's read in full). Skimmed, as mechanical: the service test diffs (`with Held`, `r.body.body` to `r.body.bytes`), the 21 `build.sbt` and `service.json` version changes, manifests, fixtures. The `DescriptionSuite` of ingest, engagement and support-agent and the `describe.env` files were read by their commit messages and research notes only. Opened outside the diff: ankka at `v0.18.0` (`HttpEndpoint.encode`, the codecs' content types, `HeldToDocument`), `tools/modules/.../BrandCommands.scala`, `sdk/player/src/server/session.ts`, game-provider's `CatalogueReads.toJson`, `specs/027-frontend-sdk/REVIEW.md`.
**Size:** 411 files, +16239 -690; about 9,500 of those lines are generated or kept JSON, about 4,700 are hand-written Scala and TypeScript, about 2,200 are documents. That is far past where line-by-line reading finds defects, and the spec already says how it splits: two pull requests at `8ffa0f76` (see the first finding).

## Questions
- `tools/modules/src/main/scala/io/eitheror/casino/modules/Main.scala:157` — question: T029 and `contracts/runtime-check.md:21` say the check runs "in local mode and before a push to the vendor", and T029 names `BrandCommands.scala`, which the diff does not touch. `Runtimes.refusal` is called in `applyBrand` and the shared project's apply only. `values push` in vendor mode sends values, which name no runtime, so I believe there is no vendor path the check could sit on and the agent's own check covers it; if that is right, the contract and the task should say "local mode; through the vendor the agent refuses", and if there is a vendor apply I missed, it lacks the call.
  Answered: that is right. The tool applies in local mode only; `values push` sends a brand's values, which name no runtime, and the vendor's agent applies and makes ankka's own check. `contracts/runtime-check.md` now says so (029d3064); T029's mention of `BrandCommands.scala` and a vendor push was wrong and nothing lacks the call.
- `contract/src/main/scala/io/eitheror/casino/contract/port/DescriptionCheck.scala:26` — thought: 400, 401, 403, 413, 500, 503 and 504 pass unnamed in both the description check and the held kits (ankka's rule, copied). A route that stops naming its own `403 player_id_mismatch` or `503 service_unavailable` is therefore caught by neither, though FR-008 asks for every refusal. `DescriptionFeatures` could hold "a route whose handler refuses with one of these names it" for the services' own codes, if that matters enough.
  Answered: the pass-through statuses are ankka's rule, kept so that the held kits and ankka's own hold agree; a route's own codes among them are named in its `refuses(…)` today by hand, and nothing fails when one is dropped. Tightening it for the services' own codes is not done here and is not among the points drafted for ankka; it is open.
- `sdk/player/src/core/shapes.ts` — thought: the generated shapes require every field a `Described.scala` case class gives as non-optional (a game's `developerName`, a profile's `emailVerified`, a sign-in's `pendingBonusCode`), where the hand-written parsers read only what a page used. The case classes mirror JSON built by hand in another file (`CatalogueReads.toJson` matches today), and the held kits fail on a branch a test causes; a branch no test causes that omits one field now refuses the whole answer (one such game empties the lobby). The 24 contract tests on a running brand are the only check end to end and are not in CI. Worth knowing when a handler's JSON is next edited: the description and the handler change together or the kit's hold must see it.
  Answered: agreed, and intended (FR-018: a shape that does not match is `malformed_answer`, never a silent default). The hold is what makes it safe: a handler that omits a described field fails its service's kit in any test that reaches the branch. A branch no test reaches is the remaining exposure, as the note says.
- `services/players/src/test/scala/io/eitheror/casino/players/it/Kit.scala:262` — question: `Kit.started` is one set per JVM and `assertHeld()` runs after each test over every kit started. Where two suites run in one JVM at once, can one suite's `afterEach` report or clear a violation another suite's request caused? If suites in a fork are sequential (players' `testGrouping`), a sentence in `Held.scala` saying so settles it.
